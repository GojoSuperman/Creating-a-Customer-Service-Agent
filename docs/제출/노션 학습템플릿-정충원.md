# 모두몰 음성 고객응대 에이전트 — 라우팅·그라운딩 구현 리포트 (정충원)

## 오늘의 주제

고객 응대 에이전트 만들기 — 라우팅과 그라운딩

## 오늘의 목표

라우터 만들기 — 규칙 기반 → LLM 구조화 출력 → 확신도 임계값으로 이관 판단까지

### 📌 한 줄 요약

브라우저에서 전화처럼 대화하는 쇼핑몰 상담 에이전트를 만들고, **숫자가 움직일 때마다 그 원인을 사례 단위로 읽어 기록했다.** 이 리포트에서 가장 값진 건 최종 점수가 아니라 "점수가 말해 주지 않는 것"을 찾아낸 과정이다 — 답변 통과율이 낮은 원인의 상당수가 에이전트가 아니라 **정답셋(골든셋)의 불완전성**이었고, 종합 통과율이 56.2%에서 15.6%로 떨어진 것도 성능이 아니라 **잣대가 바뀐 것**이었다.

### 📊 결과

**라우팅 (LLM 라우터 `gpt-4.1-mini`, 구조화 출력)**

| 지표 | 4클래스 (n=120) | 5클래스 · `OTHER` 포함 (n=153) |
|---|---|---|
| 정확도 | 0.933 | 0.895 |
| macro F1 | 0.937 | 0.895 |
| 확신도 보정 ECE | 0.046 | 0.013 |
| 자동화율 | 0.992 (이관 1건) | 0.980 (이관 3건) |

5클래스 수치가 낮은 것은 **성능 저하가 아니다.** 기존 4클래스 측정(`split=="eval"` 120건)은 분류체계 밖 문의를 담은 `OTHER` 33건(`split=="outscope"`)을 애초에 재지 않았고, 이번에 그 33건을 새로 포함시킨 결과다. `OTHER`를 뺀 4클래스만 다시 보면 여전히 0.933 / 0.937이다.

| 라우트별 recall (5클래스 측정) | 값 |
|---|---|
| PRODUCT_INFO | 0.967 |
| RETURN_REFUND | 0.967 |
| ORDER_PLACE | 0.933 |
| SHIPPING | 0.867 |
| **OTHER** | **0.758** (25/33) |

즉 "별도로 확보만 해 두고 대표 지표에서 빠져 있던 카테고리가 실제로 가장 약한 지점"이라는 사실이 이번에 처음 수치화됐다.

**답변 (골든셋 첫 턴 32건, `--runs 3`, judge 포함)**

| 지표 | 정의 | 값 |
|---|---|---|
| 도구 호출 적절성(엄격) | 호출 도구 집합 == 기대 도구 집합 (미호출·과다호출 모두 감점) + action 일치 | 7/32 (21.9%) |
| 답변 적절성 | must 전부 포함 + forbid 전부 미포함 (+ASK면 되묻는 형식), judge로 must 누락만 완화 | 24/32 (75.0%) |
| 종합(엄격) = 두 지표 AND | 새 요구사항("정확히 일치") 기준 | 5/32 (15.6%) |
| 종합(기존 정의, 과거 비교용) | 도구는 missing만 보고 extra 무시 + action + 답변 적절성 | 18/32 (56.3%) |

**종합(엄격) 15.6%는 과거 62.5%·56.2%와 나란히 놓을 수 없다.** 잣대가 다르다. 같은 잣대(기존 정의)로 재계산한 값은 56.3%이고, 이는 과거 기록 56.2%와 사실상 동일하다.

**답변 통과율 추이 (모두 judge 포함, 같은 "기존 정의" 잣대)**

| 시점 | 통과율 |
|---|---|
| 3차 강화 최종 (Task 4) | 62.5% (20/32) |
| 진행 상태 정합성 (Task 5) | 56.2% (18/32) |
| A/B 대조군 (규칙 5·6 제거) | 53.1% (17/32) |
| 2026-09-18 재계산 (기존 정의) | 56.3% (18/32) |

**행동 판정 혼동표 (2026-09-18 실행)**

| 기대 \ 실제 | ANSWER | ASK | OUT_OF_SCOPE |
|---|---|---|---|
| ANSWER | 20 | 2 | 0 |
| ASK | **3** | 5 | 0 |
| OUT_OF_SCOPE | 1 | 0 | 1 |

가장 위험한 칸은 **기대 ASK → 실제 ANSWER 3건**이다. 되물어야 할 때 단정해 버리는 것은 정보가 부족한 상태에서 잘못된 사실을 확정적으로 전달하는 것이라, 반대 방향(기대 ANSWER인데 되묻는 2건 — 왕복만 늘 뿐 사실 오류는 없음)보다 무겁다.

**기타**

- 회귀 스위트(인젝션 3 + 없는 ID 3): 6/6 PASS, 모든 회차에서 동일
- 단위 테스트 501건 통과 (`pytest`, 키 불필요)
- FLAP(3회 실행에서 판정이 엇갈린 케이스) 2건: C-001, C-015. 표본이 32건이라 **1건 = 약 3.1%p**이고, FLAP 2건은 종합 지표를 최대 ±6.2%p 흔들 수 있다.

### 🔧 한 일 (바꾼 것 요약)

| 영역 | 구현 |
|---|---|
| 라우터 | `server/router.py` — `classify`(모델) → `gate`(정책) 두 노드 그래프. 모델이 하는 일과 정책이 정하는 일을 분리해, 임계값만 바꿀 때 모델을 다시 부르지 않고 `classify`를 가짜 함수로 바꿔 LLM 없이 그래프 흐름을 시험할 수 있게 했다. |
| 구조화 출력 | `RouteDecision`(pydantic) — `route` / `confidence` / `reason` / `route_alt` / `alt_confidence` / `is_followup`. 2순위 라우트까지 받아 "얼마나 애매한가"를 수치로 꺼냈다. |
| 이관 판단 | 확신도 임계값(`CONF_THRESHOLD=0.5`) **+ 마진 게이트**(`CONF_MARGIN=0.3`, 마진 = 1순위 확신도 − 2순위 확신도). 임계값만으로는 "둘 다 0.9"인 애매한 케이스가 그대로 통과한다. |
| 매뉴얼 분할 | `server/context.py` — 매뉴얼을 `## ` 헤딩 단위로 자르고(`split_sections`) 라우트별 `always_sections + routes[route].sections`만 이어붙인다. 전문을 안 넣는 이유는 비용·지연과, 관련 없는 정책이 오답을 유도하기 때문(배송 문의에 반품 배송비가 섞이는 식). 실제로 SHIPPING 컨텍스트에 `6.1 반품 배송비`가 없고 RETURN_REFUND에 `4.1 배송비`가 없음을 직접 실행해 확인했다. |
| 조회 도구 | `server/tools.py` — 도구 10개(조회 9개: `search_product`, `get_order_status`, `get_product_detail`, `get_product_options`, `get_shipping_policy`, `get_return_policy`, `get_return_status`, `get_restock_info`, `find_customer` + 이관 1개: `escalate_to_agent`). SQLite 목 DB(상품 180·주문 480) 위에서 돈다. |
| 모델 스스로 도구 호출 | `server/answer.py`의 도구 호출 루프(`MAX_TOOL_TURNS=4`). 프롬프트(`server/prompts.py`)에 "상품을 이름으로 말했으면 먼저 `search_product`" → "`resolved_product_id`로 조회" 순서를 명시. |
| 가드레일 4종 | `server/guardrail.py` — 출처 불명 수치(`VIOLATION_UNSOURCED`), 툴 미호출 단정(`VIOLATION_NO_TOOL`), 미확정값 확답(`VIOLATION_ASSERT_UNCONFIRMED`), 진행 중 상태 누락(`VIOLATION_STALE_STATE`). 허용 집합 = 조회 결과 + 도메인 고정값 + 한 단계 산술 유도값이고, "4만 원"도 40000으로 정규화해 비교한다. 위반 시 재시도, 그래도 안 되면 이관. |
| 평가 | `eval/eval_router.py`(4클래스 / `--with-other` 5클래스 / `--multiturn`), `eval/eval_hard.py`(어려운 케이스 72건 + 임계값×마진 격자), `eval/eval_answer.py`(골든셋 `--runs 3 --judge`), `eval/eval_regression.py`, `eval/eval_context.py`. 채점기는 `eval/scoring.py`, LLM judge는 `eval/judge.py`, 확신도 보정표·ECE는 `eval/calibration.py`. |
| 채점기의 타당성 검사 | 채점기 자기검증(모범 답안을 그대로 채점기에 넣어 전부 통과하는지), judge 자기검증(모범 답안을 답변으로 넣고 must 전부를 누락 목록으로 넘겨 통과하는지 — 실패하면 평가 자체를 중단). 두 자기검증 모두 실패 0건. |
| 부가 | 음성 STT/TTS + 한국어 발음 정규화(`server/pronounce.py`), 어드민 콘솔(Basic 인증 fail-closed), 쇼핑몰(`/shop`, 전화번호 로그인 → 그 고객으로 통화), BYOK 배포(`X-OpenAI-Key` 헤더, 키가 서버·DB·로그에 남지 않음). |

### 💡 배운 것

**1. 점수만 보고 고치면 엉뚱한 곳을 손댄다 — 실패 사례는 직접 읽어야 한다**

도구 호출 적절성이 21.9%로 나왔을 때, 처음 떠오른 건 "프롬프트에 도구 사용 규칙을 더 넣자"였다. 그런데 실제로 골든셋 파일을 열어 34건의 `expect.tools`를 전부 집계해 보니 `search_product`가 **단 한 번도 없었다**. 반면 이번 실행의 과다호출 분포는 `search_product`가 15건으로 압도적이었다.

이유는 단순하다. 고객이 "가죽 벨트"처럼 **상품명**으로 말하면 에이전트는 `search_product`로 이름 → `product_id`를 해석한 뒤에야 `get_product_detail`을 부를 수 있다. 골든셋은 최종 조회 도구만 적고 그 앞의 해석 단계를 빠뜨린 것이다. 실패 27건 중 11건이 정확히 이 갈래였다 — **에이전트가 틀린 게 아니라 정답셋이 불완전했다.**

이걸 모른 채 프롬프트를 고쳤다면 멀쩡히 동작하는 부분을 망가뜨렸을 것이다. 회차 5·6이 정확히 그 실패였다(프롬프트로 도구 호출을 유도했더니 통과율이 오히려 떨어져 전부 revert).

**2. 지표 정의가 바뀌면 과거 수치와 비교할 수 없다**

`score_tools`를 "정확히 일치"로 엄격화한 뒤 종합 통과율이 15.6%로 찍혔는데, 로그의 그 줄 라벨이 "기존 지표와 비교용"이라고 적혀 있었다. **틀린 라벨이다.** 하마터면 15.6%를 과거 56.2% 옆에 나란히 놓고 "크게 나빠졌다"고 쓸 뻔했다.

옛 정의를 `score_tools_legacy`로 보존해 같은 잣대로 재계산하니 **56.3%** — 과거 56.2%와 사실상 같았다. 즉 성능이 아니라 **잣대가 변한 것**이었다. 이후 평가 스크립트가 네 지표를 라벨을 구분해 찍도록 고쳤다. 지표는 값보다 **정의와 라벨**이 먼저다.

**3. 원인을 좁히려면 대조군을 만들어야 한다**

진행 상태 정합성 작업 후 통과율이 62.5% → 56.2%로 떨어졌다. 변경이 네 갈래(데이터·도구·프롬프트·가드레일)라 그냥 봐서는 어느 쪽 탓인지 알 수 없었다. 그래서 **프롬프트 규칙 5·6 두 줄만 지우고** 같은 조건으로 다시 돌렸다. 결과는 53.1% — 회복되지 않았다. 규칙이 원인이 아니라는 뜻이다.

거기서 한 단계 더 좁혔다. 기준선에는 없었는데 두 실행 **모두에서** 새로 실패한 케이스는 C-013·C-016·C-021 셋이었고, 그중 C-016은 두 실행 모두 **같은 사유**(`must 누락: "7"`)로 실패했다. C-016의 주문(O-1002)은 반품·교환 진행 중이 아니어서 `active_process`가 null인데도 실패한다 — `get_order_status`가 `active_process`·`events_note` 필드를 **모든 호출에 무조건** 붙이도록 바뀐 것이, 필드가 비어 있는 케이스에서도 도구 출력을 키워 모델이 "1~3문장" 안에서 구체적 숫자(7일)를 생략하게 만든 것으로 보인다.

**4. 지표를 하나로 합치면 위험 구분이 사라진다**

실시간 턴 품질 표시를 처음엔 총점(가중합) 하나로 설계했다. 교육자료의 "지표를 하나로 합치면 위험 구분이 사라진다"와 어긋난다는 걸 알고 **능력·안전 두 축** 판정으로 다시 썼다.

같은 교훈이 답변 평가에서도 그대로 재현됐다. 종합 통과율 하나만 보면 15.6%지만, 쪼개 보면 **도구 호출 적절성 21.9% / 답변 적절성 75.0%**로 완전히 다른 그림이다 — "답은 대체로 맞는데 근거를 읽는 경로가 채점 기준과 어긋난다"는 진단은 합쳐 놓은 숫자에서는 절대 나오지 않는다.

**5. 진행 중 상태를 무시하고 지나간 이력으로 답하는 버그는 한 곳만 고쳐선 안 됐다**

반품 진행 중인 주문(O-1072)에 "배송 완료됐습니다"라고 답하는 문제를 세 곳에서 함께 고쳤다.

- **도구**: `get_order_status` 응답에 진행 중인 반품·교환을 `active_process` 필드로 별도 노출 (모델에게 실제로 전달되는지를 ToolMessage 본문으로 실측 확인)
- **프롬프트**: "현재 상태는 `status`와 `active_process`이고 `events`는 지나간 이력" 우선순위 규칙 + "진행 상태를 안내할 땐 `active_process` 사실을 먼저 알린다"
- **가드레일**: `VIOLATION_STALE_STATE` — 진행 중인 반품·교환을 빠뜨린 답변을 잡아 재시도시키되, 재시도해도 안 되면 통화를 끊지 않고 원답변을 통과시킴(fail-open)

실통화 재현 4/4 성공. **다만 이 수정이 골든셋 통과율에는 잡히지 않는다** — `eval_answer`는 `Answerer`를 직접 호출해 파이프라인(가드레일 포함)을 타지 않기 때문이다. 가드레일의 효과는 실통화 재현과 회귀 스위트에서만 확인된다. 평가 스크립트가 무엇을 재고 무엇을 안 재는지 아는 것 자체가 결과 해석의 일부다.

**6. 그리고, 실측하지 않으면 코드를 의심하게 된다**

같은 작업 중에 "DB를 고쳤는데 반영이 안 된다"는 현상이 있었다. 오래 떠 있던 서버 프로세스가 삭제된 SQLite 파일을 붙들고 있었던 것이지 코드 결함이 아니었다. 서버 재시작 한 번으로 끝났다.

### ⚠ 한계와 채점기의 한계

**표본과 변동성**

- 답변 골든셋이 **32건**이라 **1건 = 약 3.1%p**다. 등락을 그대로 성능 변화로 읽으면 안 된다.
- FLAP 2건(C-001, C-015)은 3회 실행에서 판정이 엇갈린 케이스다. 이 2건을 어느 쪽으로 세느냐에 따라 종합 지표가 **±6.2%p** 움직인다.
- 회차 11(A/B 대조군)의 53.1%는 56.2%보다 1건 낮지만, FLAP이 2건 → 3건으로 늘어난 것을 감안하면 **오차 범위 안**으로 봐야 한다.

**채점기 자체의 한계**

- 규칙 채점기는 **문자열 포함** 여부로 본다. "품절"과 "재고가 없습니다"를 다르게 취급한다. LLM judge를 붙여 must 누락 건만 완화했지만, judge는 rubric·reference가 틀리면 같이 틀린다. 자기검증(모범 답안이 전부 통과하는지)이 그 최소 방어다.
- judge는 **must 누락만** 본다. action·tools·forbid·ASK 형식 실패는 judge로 완화하지 않는다.
- `infer_action`(`server/pipeline.py`)의 판정 경계가 애매하다. C-015("주문 정보를 확인할 수 없습니다. 주문번호를 알려주시면…")와 C-027("지역에 따라 다릅니다. 지역을 알려주시면…")은 **문장 자체는 되묻는 형태인데** ANSWER로 잡혔다. C-034는 A/S를 정중히 안내·거절하는 상식적으로 적절한 응대인데 OUT_OF_SCOPE가 아니라 ANSWER로 분류됐다. **답변 품질과 채점 결과가 어긋나는 사례**다.
- 가드레일의 `VIOLATION_STALE_STATE`는 판정기가 아니라 **안전망**이다. 답변에 "반품·교환·수거·검품·환불·입고" 중 한 단어라도 있으면 문맥과 무관하게 통과시킨다("반품 규정은 7일입니다"처럼 무관한 문장이어도 통과).
- 종합(기존 정의) 56.3%는 **근사치**다. 로그에 찍힌 실패 사유는 3회 중 **첫 번째 run**의 것이라, 재분류한 13건이 나머지 두 run에서도 동일하게 "과다호출뿐"이었는지는 로그만으로 확인할 수 없다. 정확한 값을 얻으려면 재실행이 필요한데 비용 문제로 보류했다.

**평가 범위의 한계**

- `eval_answer`는 파이프라인(라우터 → 가드레일 → 재시도)을 거치지 않는다. 가드레일의 효과와 부작용은 이 수치에 **전혀 잡히지 않는다.**
- 가드레일이 라우트 기준(SHIPPING·RETURN_REFUND 한정)이라, `ORDER_PLACE`로 분류된 상태 질문은 놓친다(fail-open). 골든셋 C-016이 정확히 이 경우라 커버리지 0건이다.
- `routing_answers.csv`의 `split="fewshot"` 40건은 런타임 프롬프트 어디에도 주입되지 않는다(저장소 전체에서 이 CSV를 읽는 코드는 평가 스크립트 둘뿐). 라우터가 보는 것은 `domain.json`의 정의·규칙 텍스트뿐이다.

**시스템 자체의 한계**

- 상품명 연결이 토큰 겹침 + 오타 보정 수준이다. 실서비스는 임베딩 검색이 필요하다.
- 체크포인터가 메모리라 서버를 재시작하면 통화가 사라진다.
- 전화번호만으로 고객을 식별한다(본인 인증 없음). 환불 계좌 변경 같은 민감 처리는 이관으로 뺀다.
- 라우터 과신이 마진 게이트의 한계다. 경계모호 15건이 확신도 0.7~0.9 구간에 몰려 있고, 마진 게이트를 넣은 뒤에도 위험 10건이 남았다. **임계값×마진 격자 어디에도 목표(5건 이하)를 만족하는 조합이 없었다.**
- `OTHER` recall 0.758의 오분류 대부분은 확신도 게이트를 통과해 자동 처리로 샌다(이관 3건/153건). 게이트가 이 오류를 걸러 주지 못한다.

**고치지 않고 남긴 것**

골든셋에 `search_product`를 추가하면 (A) 갈래 11건이 사라지고 엄격 지표가 크게 오른다. 그런데 **이번에는 고치지 않았다.**

"채점 결과에 맞춰 정답을 고치는" 함정과 구분이 필요하기 때문이다. `search_product`가 34건의 기대 도구에 하나도 없다는 사실은 골든셋 파일을 그대로 읽어서 나온 것이지 실패 사례에서 역산한 게 아니고, "상품명 → ID 해석에 `search_product`가 필요하다"는 건 에이전트가 무엇을 답했는지와 무관하게 참인 도메인 사실이다. 그럼에도 **"11건이 딱 이 갈래에 걸린다"는 것 자체는 실패를 보고 나서 확인된 사실**이다. 그래서 고치려면 별도 리뷰 절차(무엇을 언제 부르는 게 정답인지 도메인 담당자 확인)를 거쳐야 "결과에 맞춘 수정"이 아니라 "도메인 사실 보강"이라고 방어할 수 있다고 판단했다.

| **잘 된 것** | 숫자가 움직일 때마다 **실패 사례를 직접 읽어** 원인을 갈래로 나눈 것. 그 덕에 "도구 호출 적절성 21.9%"가 에이전트 문제가 아니라 골든셋 결함이라는 걸 찾았고, 엉뚱한 곳을 고치지 않았다. 통과율 하락의 원인을 **A/B 대조군**(규칙 5·6만 제거, 53.1%)으로 좁힌 것, 그리고 옛 채점 정의를 `score_tools_legacy`로 보존해 과거 수치와 비교 가능성을 지킨 것. 측정 기록을 4개 문서로 남겨 README의 모든 숫자가 어느 실행에서 나왔는지 추적 가능하게 한 것. |
| **헛디딘 것** | 프롬프트에 "라우트별 필수 도구 표 + 자기 점검"을 넣으면 도구 미호출이 줄 거라 예상했는데 **65.6% → 53.1%로 떨어졌고**, 표만 남긴 2차는 46.9%로 더 떨어져 전부 revert했다. 실시간 턴 채점을 처음부터 총점(가중합) 방식으로 설계했다가 교육자료와 어긋남을 알고 두 축으로 다시 쓴 것. `get_order_status`에 `active_process`를 **모든 호출에 무조건** 붙인 것 — 필드가 비어 있는 케이스까지 출력이 커져 통과율 하락에 기여한 것으로 보인다. 그리고 엄격 지표의 종합 줄에 "기존 지표와 비교용"이라는 **틀린 라벨**을 붙여 둔 것. |
| **놀란 것** | 골든셋 34건의 기대 도구에 `search_product`가 **단 한 번도 없다**는 것 — 정답셋이 이렇게 명확하게 비어 있을 줄 몰랐다. 옛 정의로 재계산한 56.3%가 과거 기록 56.2%와 **소수점까지 사실상 일치**한 것도 놀랐다(잣대만 바꿔 놓고 성능이 반의 반토막 났다고 볼 뻔했다). 멀티턴에서 직전 라우트를 이어받게 하면 좋아질 줄 알았는데 **턴2+ 정확도가 0.957 → 0.870으로 오히려 떨어진 것**. 그리고 DB 수정이 반영 안 되는 게 코드 결함이 아니라 **오래 떠 있던 서버가 삭제된 파일을 붙들고 있었던 것**. |
