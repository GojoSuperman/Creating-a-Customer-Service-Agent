# 2026-09-18 OTHER 포함 5클래스 라우팅 측정

## 배경 — 왜 재는가

`domains/modumall/eval/routing_answers.csv` 에는 분류체계 밖 문의를 담는 `OTHER` 카테고리가 33건
(`split="outscope"`) 확보돼 있다. 그런데 `eval/eval_router.py` 의 기존 측정(정확도 0.933 / macro F1 0.937,
`docs/측정기록/2026-09-17 3차 강화 측정.md` §9)은 `LABELS4 = [ORDER_PLACE, PRODUCT_INFO, SHIPPING,
RETURN_REFUND]` 로 `OTHER` 를 빼고, `split == "eval"` 120건만 쓴다 — `OTHER` 33건은 대표 지표 어디에도
반영되지 않는다. "별도로 확보한 카테고리"의 성능 숫자가 없는 상태였다.

이번 측정은 `OTHER` 를 포함한 5클래스로 `eval`(120건) + `outscope`(33건) = 153건을 측정해 그 빈자리를
채운다. `eval/eval_router.py` 에 `--with-other` 옵트인 플래그를 추가했다(기본 4클래스 동작·출력은 그대로
보존, 기존 측정 0.933/0.937 과의 비교 가능성을 깨지 않는다).

브랜치 `feat/voice-agent`. 명령은 저장소 루트에서 `.venv/bin/python` 으로 실행했다.

## 1. 5클래스 측정 (OTHER 포함, 153건)

- 모델: `gpt-4.1-mini` (`.env` 의 `OPENAI_API_KEY` 사용)

## 2. 4클래스 결과와의 비교

| | 4클래스 (기존, 120건) | 5클래스 +OTHER (153건) |
|---|---|---|
| 정확도 | 0.933 | 0.895 |
| macro F1 | 0.937 | 0.895 |
| 대상 | `split=="eval"` 만 | `split` in `{eval, outscope}` |

정확도 −3.8%p, macro F1 −4.2%p 로 하락했다. 이는 라우터가 갑자기 나빠졌다는 뜻이 아니라, 기존 4클래스
측정이 애초에 재지 않던 33건(`OTHER`)을 새로 포함시켰기 때문에 나온 자연스러운 차이다. `OTHER` 자체의
recall 이 0.758(25/33)로 네 라우트의 recall(0.867~0.967)보다 뚜렷이 낮고, 이 낮은 recall 이 macro F1 을
끌어내렸다 — `OTHER` 를 뺀 4클래스만 다시 집계하면(4클래스 지표는 위 표 그대로) 여전히 0.933/0.937 수준이라,
4클래스 문의 자체의 분류력은 두 측정 사이에 실질적으로 달라지지 않았다. 즉 "별도 확보한 미분류 카테고리는
확보만 해두고 성능이 가장 약한 지점"이라는 것이 이번 측정으로 처음 수치화됐다.

## 3. `OTHER` 오분류 8건 — 실제로 읽고 원인 구분

`OTHER` 33건 중 오분류는 8건(recall 0.758). 문항을 직접 읽고 원인을 두 갈래로 나눴다.

**(A) 도메인 정의가 이 하위유형을 아예 언급하지 않음 — 5건**
`domains/modumall/domain.json` 의 `OTHER` 판단 규칙(매뉴얼 7.1)은 "매장 위치·영업시간·주차, 타 오픈마켓
주문, 제조사 A/S" 세 가지만 명시한다. 아래는 이 세 가지 어디에도 해당하지 않는, 정의에 없는 회색지대다.
모델이 정의에 없으니 가장 가까운 어휘로 끌려가 다른 라우트를 골랐다.
- "장바구니에 담아둔 게 사라졌어요." → ORDER_PLACE (사이트 버그 신고인데 "장바구니"→주문 어휘로 흡수)
- "재입고되면 알림을 받을 수 있나요?" → PRODUCT_INFO (알림 기능 문의인데 "재입고"→상품 어휘로 흡수)
- "메시지 카드를 같이 넣어주실 수 있나요?" → ORDER_PLACE (포장 부가서비스 요청)
- "포장이 찌그러진 채로 왔는데 어디에 말해야 하나요?" → RETURN_REFUND (파손 배송 클레임 — RETURN_REFUND 와
  경계가 가장 가깝지만, 매뉴얼에 "파손 수령"에 대한 명시적 처리 규정이 없어 정답은 OTHER 로 잡혀 있다)
- "박스가 아니라 봉투로 받아볼 수 있을까요?" → SHIPPING (포장 방식 선택 요청)

**(B) "예약/사전 주문" 의도 — 정의는 있지만 어휘 신호가 압도적으로 강함 — 3건**
- "시착만 해보고 온라인에서 주문해도 되나요?"
- "출시 전에 미리 주문해 둘 수 있는지 궁금합니다."
- "예약 구매는 언제부터 가능한가요?"

모두몰이 사전 예약 판매를 지원하지 않는다는 전제로 정답이 OTHER 인데, 세 문장 모두 "주문"이라는 낱말을
직접 포함해 ORDER_PLACE 쪽 어휘 신호가 매우 강하다. 라우터 프롬프트(`server/prompts.py`
`build_route_guide`)의 "고객이 쓴 단어가 아니라 원하는 결과로 판단하라"는 원칙이 이 세 건에서는 작동하지
않았다 — "예약 구매가 가능한 서비스인지" 자체가 매뉴얼에 없어 모델이 판단할 근거가 없다.

**역방향도 1건 있다**: `[SHIPPING → OTHER]` "주소를 잘못 입력한 것 같은데 어떻게 하면 좋을까요?" — 정답은
SHIPPING(배송지 정정 요청)인데 모델이 OTHER 로 과잉 판단했다. 확신도 0.90 으로 이관 게이트를 통과하지 못해
실제 서비스에서는 이관되므로 피해는 크지 않지만, `OTHER` 로의 오탐도 존재함을 보여준다.

**참고로 확인한 별개 사실**: `routing_answers.csv` 의 `split="fewshot"`(40건, `OTHER` 는 0건)은 실제
런타임 프롬프트 어디에도 주입되지 않는다(`server/router.py::make_llm_classifier` 는 `build_route_guide` 만
쓰고, 저장소 전체에서 `routing_answers.csv`/`customer_inquiries.csv` 를 읽는 코드는 `eval/eval_router.py`
와 `eval/eval_context.py` 뿐 — 둘 다 평가용이다). 즉 라우터가 보는 것은 `domain.json` 의 정의·규칙 텍스트뿐이고,
`OTHER` 는 정의 텍스트 자체가 세 가지 예시로 좁게 쓰여 있다는 것이 (A) 5건의 근본 원인이다.

## 4. 해석 요약

- `OTHER` 를 포함해도 전체 정확도 0.895 로 실사용 기준으로는 여전히 준수하다. 다만 `OTHER` 만 떼어보면
  recall 0.758 로 네 라우트 중 가장 낮고, 확신도 게이트(임계값 0.5·마진 0.3) 를 통과해 자동 처리(HANDLE/
  OUT_OF_SCOPE)로 새는 오분류가 8건 중 다수라 — 이관 3건/153건(0.980 자동화율)만으로는 `OTHER` 오분류
  대부분이 걸러지지 않는다는 뜻이다.
- 개선 방향은 두 가지로 갈린다: (A) 유형은 `domain.json` 의 OTHER 판단 규칙에 "포장·배송 부가요청,
  사이트 기능 문의, 파손 수령" 같은 예시를 추가하면 바로 줄어들 여지가 있다. (B) 유형(예약 주문)은 "모두몰은
  예약 판매를 하지 않는다"는 문장 한 줄을 매뉴얼/규칙에 추가하는 것으로 해결될 가능성이 높다. 이번 작업
  범위(측정 인프라 추가)에서는 코드를 더 건드리지 않고 수치와 원인만 남긴다.
