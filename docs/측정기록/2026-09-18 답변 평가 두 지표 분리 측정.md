# 2026-09-18 답변 평가 두 지표 분리 측정

## 배경 — 왜 재는가

`eval/scoring.py::score_tools`가 도구 호출 적절성을 "기대 도구 부족분(missing)만 감점"에서
"**집합 정확 일치**(need == got, 초과 호출(extra)도 감점)"로 엄격해졌다. 과제 요구사항 원문이 "정확히
일치"이므로 이 변경 자체는 맞다. 그런데 이 변경 때문에 `eval/eval_answer.py`가 찍는 종합 통과율이
15.6%(5/32)까지 떨어졌고, 그 줄의 라벨이 "기존 지표와 비교용"이라 적혀 있었다 — **틀린 라벨이다.**
잣대가 바뀌었으니 과거 62.5%(Task 4)·56.2%(Task 5, `README.md` 표 행 4·5)와 나란히 놓으면 안 된다.

먼저 실측으로 원인을 확인했다: `domains/modumall/eval/answer_goldenset.json`의 `expect.tools`를
전부 집계하면 `search_product`는 34건 중 **단 한 번도** 기대 도구에 없다(`get_product_detail 8·
get_shipping_policy 5·get_return_status 5·get_product_options 3·get_order_status 2·
get_return_policy 2·get_restock_info 1·escalate_to_agent 1`). 하지만 이번 실행의 과다호출 분포는
`search_product 15·get_order_status 4·find_customer 3·get_return_status 2·get_product_options 2·
get_shipping_policy 1·get_product_detail 1`이다. 고객이 "가죽 벨트"처럼 상품명으로 말하면 에이전트는
`search_product`로 이름→product_id를 해석한 뒤에야 `get_product_detail`을 부를 수 있는데, 골든셋은
최종 조회 도구만 적고 그 앞 해석 단계를 빠뜨렸다. 즉 엄격 지표 실패의 상당수는 정답셋의 불완전성이지
에이전트 오작동이 아니다.

이번 작업은 (1) `eval_answer.py`/`eval/scoring.py`에 **세 지표를 라벨을 바로잡아 구분 출력**하고,
(2) 이미 끝난 실행 로그(`logs/eval-answer-two-metrics.log`, 재실행 안 함)에서 "기존 정의" 수치를
유도하고, (3) 실패 사례를 직접 읽어 원인을 갈래별로 나눈다. **골든셋은 고치지 않았다** — 이번에는
사실만 기록한다.

브랜치 `feat/voice-agent`. 로그는 이미 실행된 것을 그대로 쓴다(재실행 없음, 비용·시간 절약).

## 1. 세 지표 — 정의를 바로잡아 구분

기존 로그의 두 번째 줄 라벨(`[종합 통과율 — 기존 지표와 비교용, 두 지표 AND]`)이 틀렸다. `score_tools`가
엄격 정의로 바뀐 뒤에는 그 종합이 과거 기록과 **비교 불가**하다. `eval/scoring.py`에 옛 정의를 보존한
`score_tools_legacy`(missing만 보고 extra는 무시)를 추가하고, `eval/eval_answer.py`가 이제 아래 네 줄을
찍도록 고쳤다(코드는 이번에 고쳤고, 아래 수치는 **이미 끝난 로그에서 수작업으로 유도**한 것이지 새로
측정한 것이 아니다 — §2 참고).

| 지표 | 정의 | 이번 실행 수치 |
|---|---|---|
| 도구 호출 적절성(엄격) | 실제 호출 도구 집합 == 기대 도구 집합 (missing·extra 모두 감점) + action 일치 | **7/32 (21.9%)** |
| 답변 적절성 | must 전부 포함 + forbid 전부 미포함 (+ASK면 되묻는 형식) — judge로 must 누락만 완화 | **24/32 (75.0%)** |
| 종합(엄격) | 위 두 지표의 AND. **과거 62.5%·56.2%와 잣대가 달라 직접 비교 불가** | **5/32 (15.6%)** |
| 종합(기존 정의, 과거 비교용) | 도구는 missing만 보고 extra는 무시(옛 `score_tools`) + action + 답변 적절성의 AND | **18/32 (56.3%)** — §2에서 로그로부터 유도 |

`score_tools`(엄격)와 `score_tools_legacy`(옛 정의)는 `eval/scoring.py`에 나란히 존재한다. 다음
실행부터는 `eval_answer.py`가 네 줄(두 지표 + 종합(엄격) + 종합(기존 정의))을 자동으로 찍는다 — 이번
로그는 코드 수정 전에 실행된 것이라 종합(기존 정의) 줄이 없고, 그래서 §2 절차로 손으로 유도했다.

남기지 않음).

- 원래 판정 PASS 5건(C-003, C-005, C-006, C-031, C-032) — 엄격 정의로도 통과했으니 더 관대한 옛 정의로도

## 3. 행동 판정 혼동표

```
실제            ANSWER  ASK  OUT_OF_SCOPE
기대
ANSWER            20    2             0
ASK                3    5             0
OUT_OF_SCOPE       1    0             1
```

가장 위험한 칸은 **기대 ASK → 실제 ANSWER (3건)**이다 — 되물어야 할 때 단정해 버리는 것은, 정보가
부족한 상태에서 잘못된 사실을 확정적으로 전달할 위험이 있어 반대 방향(기대 ANSWER인데 되묻는 것, 2건 —
불필요한 왕복만 생길 뿐 사실 오류 위험은 없음)보다 심각하다. 이 3건:

- **C-009**: 고객 문의는 화장품(트래블 키트) 반품 가능 여부. 기대는 ASK(구매일 확인 등 필요)인데 실제
  답변은 "8월 초에 구매하셨으니 기간은 지났지만…"으로 **확정 답변**했다 — 구매일을 가정하고 단정한
  것으로 보인다.
- **C-015**: 주문 정보 조회 실패 상황. 기대는 ASK(주문번호를 되물어야 함)인데 실제 답변 "고객님의 주문
  정보를 확인할 수 없습니다. 주문번호를 알려주시면…"은 텍스트상 되묻는 문장을 포함하지만 `infer_action`이
  ANSWER로 판정했다 — 뒤 §4 FLAP에서 다시 다룬다.
- **C-027**: "티셔츠의 당일배송 가능 여부는 지역에 따라 다릅니다. 배송받으실 지역을 알려주시면
  확인해드리겠습니다." — 이것도 문장 자체는 되묻는 형태에 가까운데 action이 ANSWER로 잡혔다. C-015·C-027
  둘 다 "정보를 안내하면서 동시에 되묻는" 혼합 문장이라 `infer_action`(`server/pipeline.py`)의 판정
  경계가 애매한 사례로 보인다 — 이번 작업 범위에서는 코드를 고치지 않고 사실만 남긴다.

## 5. FLAP 2건 — C-001, C-015

```
FLAP C-001: ok | action: 기대 ASK != 실제 ANSWER | action: 기대 ASK != 실제 ANSWER
FLAP C-015: tools 과다호출: ['find_customer']; action: 기대 ASK != 실 | tools 과다호출: ['find_customer']; action: 기대 ASK != 실 | ok
```

- **C-001**: 3회 중 1회만 규칙을 전부 통과(`ok`)하고 나머지 2회는 기대 ASK인데 실제 ANSWER로 판정됐다.
  첫 run의 답변("모두몰의 기본 배송비는 2,500원입니다. 추가로 궁금하신 점 있으실까요?")은 사실을 먼저
  안내하고 끝에 여지를 남기는 문장이라, run마다 되묻는 문장 유무가 갈렸을 가능성이 있다.
- **C-015**: 3회 중 2회는 `find_customer` 과다호출 + action 오판, 1회만 통과(`ok`). §3에서 본 것처럼
  "정보를 확인할 수 없습니다. 주문번호를 알려주시면…" 같은 혼합 문장이 `infer_action` 판정 경계에 걸려
  run마다 흔들리는 것으로 보인다.

**노이즈 크기**: 표본이 32건이라 **1건 차이가 약 3.1%p**를 움직인다(`README.md` 기존 서술과 동일한
경고). FLAP 2건은 "판정 자체가 흔들리는 입력"이라는 뜻이라, 이 2건의 방향을 어느 쪽으로 세든 종합(엄격)
지표가 최대 ±6.2%p(2/32) 움직일 수 있다는 뜻이다. 등락을 그대로 성능 변화로 읽지 않는다.

## 6. 다음에 할 일 — 골든셋은 이번에 고치지 않는다

(A) 갈래(11건, 40.7%)를 고치려면 골든셋의 `expect.tools`에 `search_product`(상품명→ID 해석 단계)를
추가해야 한다. 이것이 "채점 결과에 맞추기"의 함정과 다른 이유:

- 함정은 **관찰된 실패를 없애기 위해 정답 자체를 답에 맞춰 고치는 것**이다(예: 에이전트가 틀린 사실을
  말했는데 must 항목을 그 틀린 사실에 맞게 바꾸는 것). 그렇게 하면 지표는 좋아지지만 실제 에이전트
  품질은 그대로다.
- 반면 `search_product` 추가는 **정답셋이 실제로 필요한 단계를 빠뜨렸다는 것을 먼저 실측으로 확인**한
  뒤(§ 배경의 34건 기대 도구 집계 — `search_product`가 한 번도 없다는 사실은 골든셋 파일을 그대로 읽어서
  나온 것이지 실패 사례에서 역산한 게 아니다) 그 빠진 단계를 채우는 것이다. 에이전트의 답변 내용은
  건드리지 않는다 — "상품명→ID 해석에 search_product가 필요하다"는 도메인 사실은 에이전트가 무엇을
  답했는지와 무관하게 참이다.
- 다만 이번 보고서에서 **11건이 딱 이 갈래에 걸린다는 것 자체가 "실패를 보고 나서" 확인된 사실**이라는
  점은 인정해야 한다. 그래서 이번에는 **고치지 않고 사실만 남긴다** — 골든셋을 고치는 작업은 별도 리뷰
  절차(무엇을 언제 부르는 게 "정답"인지 도메인 담당자 확인 등)를 거쳐야 "결과에 맞춘 수정"이 아니라
  "도메인 사실 보강"이라고 방어할 수 있다.
- (B)(2건, C-008·C-030) 진짜 과다호출은 골든셋과 무관한 에이전트 동작 문제이므로 프롬프트/도구 사용
  전략을 봐야 한다.
- (C)(4건) 필수 도구 미호출, 특히 C-019(재고 확인 안 하고 "바로 구매 가능"이라 단정)는 사실 오류로
  이어질 수 있어 (D)보다 먼저 볼 가치가 있다.
- (E) 중 C-015·C-027·C-034는 답변 내용 자체는 크게 나쁘지 않은데 `infer_action`(`server/pipeline.py`)
  판정이 흔들리는 패턴이 반복된다 — 판정 로직 자체를 다음 조사 대상으로 남긴다.
