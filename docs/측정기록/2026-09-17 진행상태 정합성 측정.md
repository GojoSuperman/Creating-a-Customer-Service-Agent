README 5행의 숫자가 어느 실행에서 나왔는지 추적한다. `logs/` 는 gitignore 대상이라 원본 파일은 커밋되지 않으므로,
여기에 로그 이름·실행 명령·요약 블록만 그대로 옮겨 둔다. 요약 블록은 로그에서 손대지 않고 복사한 것이다.

## 배경 — 고친 것 4줄

사용자가 반품 진행 중인 주문(O-1072)으로 배송을 물었을 때 답변이 반품 사실을 빠뜨리는 문제를 고쳤다
(commits `f313e22..8376ef5`).

1. **데이터 정합성** — 반품·교환 주문의 `status_detail` 을 반품 단계에서 파생시키고, 종결 상태로 `반품완료`·`교환완료` 를 신설(`f313e22`, `db5c6d2`). 교환 주문에 환불 문구가 섞여 나가던 것도 함께 제거.
2. **도구 `active_process`** — `get_order_status` 응답에 진행 중인 반품/교환을 별도 필드로 노출(`0e94bc3`). ToolNode 의 ToolMessage 본문으로 모델에게 실제 전달되는 것을 가짜 LLM 메시지 덤프로 실측 확인.
3. **프롬프트 규칙 5·6** — "현재 상태는 status 와 active_process" 우선순위, "진행 상태를 묻거나 안내할 때는 active_process 사실을 먼저 알리고" 규칙 추가(`4a4da7e`, `fa319a4` 로 대상·범위 명확화). 프롬프트 +49자.
4. **가드레일 `VIOLATION_STALE_STATE`** — 진행 중인 반품·교환을 빠뜨린 답변을 Pipeline 경유 시 잡아 재시도시킴. SHIPPING·RETURN_REFUND 라우트로 범위를 좁히고, 재시도해도 안 되면 통화를 끊지 않고 원답변을 통과시킴(`df06e10`, `8376ef5`).

## 1. 실통화 재현

`O-1072`(반품 진행 중) 고객으로 전화해 "배송 조회 좀 부탁해" 계열 4가지 표현으로 물었을 때, 4가지 모두
반품 진행 사실을 먼저 안내함을 확인했다. 예:

> "지금 주문하신 건은 반품 수거가 끝나서 입고를 기다리고 있습니다. 배송은 이미 9월 14일에 완료됐습니다…"

부수 발견: 오래 떠 있던 서버 프로세스가 낡은 SQLite 커넥션을 붙들고 있어 DB 변경(위 1번)이 반영되지 않았고,
그 서버로 재현했을 때는 7/7 케이스 모두 반품 사실을 빠뜨렸다. 코드 결함이 아니라 서버 재시작이 필요했던
것으로, README 의 "테스트 후 서버 재시작" 주의와 같은 종류의 함정이다.

### 2-1. 되돌림 실험 — `server/prompts.py` 절대 규칙 5·6 임시 제거 (429로 미완주)

원인이 이번 작업(규칙 5·6)인지, 이전 작업(Task 1 데이터·Task 2 도구)인지 가르기 위해 규칙 5·6 두 줄만
지우고(7~9번을 5~7번으로 당김) 같은 조건으로 재측정을 시도했다.

- 로그: `logs/eval-answer-judge-rules56-removed.log`
- 명령: `.venv/bin/python -m eval.eval_answer --workers 1 --runs 3 --judge 2>&1 | tee logs/eval-answer-judge-rules56-removed.log`
- 결과: **`OpenAIRateLimitError` (429) 로 중도 종료**. 채점 도중 `gpt-4.1` 조직 분당 토큰 한도(TPM 30000, 사용 25852 + 요청 4973)를 넘겨 예외로 죽었다. 무한 재시도하지 않고 그대로 기록한다.


**A/B 판정 미결**: 하락(62.5% → 56.2%)이 규칙 5·6 때문인지, Task 1(데이터)·Task 2(도구) 변경 때문인지
이번 측정으로는 가리지 못했다. `server/prompts.py` 는 즉시 원복했고 `git diff server/prompts.py` 가 빈
출력임을 확인했다(규칙 5·6 포함 원래 상태로 복귀, 커밋 트리는 "규칙 있음" 상태 유지).

**다음에 할 일**: 토큰 한도가 풀리면 규칙 5·6 제거본으로 A/B 재측정 → 56% 근처로 남으면 원인은 데이터·도구
변경 쪽, 62% 근처로 돌아오면 규칙 5·6 이 원인이므로 되돌릴지 재검토.

## 중요 주의 — eval_answer 는 가드레일을 타지 않는다

`eval_answer` 는 `Answerer` 를 직접 호출해 답변을 채점한다. Pipeline(라우터 → 가드레일 → 재시도)을 거치지
않으므로, Task 4(가드레일 `VIOLATION_STALE_STATE`)의 효과와 부작용은 이 평가로 드러나지 않는다.
가드레일 경유 여부는 §1 실통화 재현과 §4 `eval_regression` 에서만 확인된다.
