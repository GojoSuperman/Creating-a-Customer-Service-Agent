## 배경 — 고친 것 4줄

사용자가 반품 진행 중인 주문(O-1072)으로 배송을 물었을 때 답변이 반품 사실을 빠뜨리는 문제를 고쳤다
(commits `f313e22..8376ef5`).

1. **데이터 정합성** — 반품·교환 주문의 `status_detail` 을 반품 단계에서 파생시키고, 종결 상태로 `반품완료`·`교환완료` 를 신설(`f313e22`, `db5c6d2`). 교환 주문에 환불 문구가 섞여 나가던 것도 함께 제거.
2. **도구 `active_process`** — `get_order_status` 응답에 진행 중인 반품/교환을 별도 필드로 노출(`0e94bc3`). ToolNode 의 ToolMessage 본문으로 모델에게 실제 전달되는 것을 가짜 LLM 메시지 덤프로 실측 확인.
3. **프롬프트 규칙 5·6** — "현재 상태는 status 와 active_process" 우선순위, "진행 상태를 묻거나 안내할 때는 active_process 사실을 먼저 알리고" 규칙 추가(`4a4da7e`, `fa319a4` 로 대상·범위 명확화). 프롬프트 +49자.
4. **가드레일 `VIOLATION_STALE_STATE`** — 진행 중인 반품·교환을 빠뜨린 답변을 Pipeline 경유 시 잡아 재시도시킴. SHIPPING·RETURN_REFUND 라우트로 범위를 좁히고, 재시도해도 안 되면 통화를 끊지 않고 원답변을 통과시킴(`df06e10`, `8376ef5`).

## 중요 주의 — eval_answer 는 가드레일을 타지 않는다

`eval_answer` 는 `Answerer` 를 직접 호출해 답변을 채점한다. Pipeline(라우터 → 가드레일 → 재시도)을 거치지
않으므로, Task 4(가드레일 `VIOLATION_STALE_STATE`)의 효과와 부작용은 이 평가로 드러나지 않는다.
가드레일 경유 여부는 §1 실통화 재현과 §4 `eval_regression` 에서만 확인된다.

- 가드레일이 라우트 기준이라 `ORDER_PLACE` 로 분류된 상태 질문은 놓친다(fail-open). 정답셋 C-016 이 이 경우라 커버리지 0건.
- `_DELIVERY_CLAIM_RE` 의 '도착' 단독 매칭이 넓어 레거시 경로에서 과탐 가능성.
- `web/panel.js` 의 `statusClass` 가 `반품완료`/`교환완료` 도 진행중 스타일(`ret`)로 칠한다 — 시각 표시뿐이고 로직에는 영향 없음.
